Engine 1 · 추천

LLM에게 “장소”를 묻지 않는다

“없는 가게를 말하지 마”라고 적어봤지만 소용없었다. 그래서 물어보는 항목 자체를 바꿨다.

⏱️ 시간 계산은 서버가
“다음 일정까지 220분”을 서버가 계산해 넘긴다. 그 안에 끝나는 활동만 올라온다.
📋 액션은 “제안”일 뿐
일정 생성을 제안해도 사용자 확인 없이는 저장되지 않는다.
💸 호출 절약
지도를 움직인다고 다시 찾지 않는다. 검색어를 바꿨을 때만 호출한다.

Engine 3 · 약속 조율

약속 조율 — 시간을 슬롯으로 쪼갠다

🔗 초대 링크
링크는 난수라 찍어서 맞힐 수 없다. 링크가 있어도 로그인하고 참여 등록을 해야 응답할 수 있다.
✏️ 응답 전체 교체
고친 칸만 보내지 않고 “내 가능한 시간” 전체를 매번 다시 보낸다. 그래서 지운 칸이 남지 않는다.
✅ 확정 3중 검증
생성자인가 · 시간 단위에 맞는가 · 구간의 모든 슬롯이 실제 후보인가.
📨 알림은 이벤트로

Engine 5 · 알림

알림 — 상황 11가지 · 메일은 그중 5가지

전부 메일로 보내지 않는다. 앱을 안 보고 있어도 놓치면 안 되는 것만 메일까지 간다.

📡 폴링하지 않는다
저장된 알림을 Redis로 publish하고 SSE로 밀어 넣는다. 화면이 주기적으로 물어보지 않는다.
🌧️ 날씨 경보는 조건이 좁다
매일 07시에 야외 할 일만 훑고, 예보가 비 또는 눈일 때만 보낸다. 흐림은 보내지 않는다.
🗑️ 약속이 지워지면 알림도 지운다
사라진 약속의 알림이 목록에 남으면 눌러도 갈 곳이 없다. 삭제 이벤트에서 같이 정리한다.

Technical Challenges

고른 것과 버린 것

네 번의 갈림길에서 무엇을 포기했는지 적었다.

추천
LLM이 없는 가게를 지어낸다
프롬프트 강화장소 DB 구축✓ 책임 분리
프롬프트는 손볼 때마다 다시 새어 나왔고, 장소 DB를 쌓는 일은 짧은 기간 동안에는 무리였다. LLM에게 장소를 묻지 않으면 지어낼 수 없다.
약속
최적 시간을 매번 계산하면 느리지 않을까
집계 컬럼 저장Redis 캐시✓ 그때그때 집계
참여자가 많아야 수십 명이라 집계가 훨씬 싸다. 저장해두면 누가 응답을 바꿀 때마다 맞춰줘야 하고, 거기서 버그가 난다.
외부 API
호출량이 사용자 수를 따라 늘어난다
사용자별 호출 제한전면 캐시✓ 좌표 반올림 + 의도 기반 호출
좌표를 100m로 묶으면 옆 사람과 캐시를 공유한다. 지도를 움직일 때가 아니라 검색어를 바꿀 때만 부르니, 호출 수가 사용자 수가 아니라 의도 수를 따라간다.
개인화
데이터가 없는 첫 사용자에게 뭘 보여줄까
인기순 고정협업 필터링✓ 3단 폴백
사용자가 적어 협업 필터링은 애초에 쓸 수 없었다. 지금 맥락 → 전체 상위 → 설문값 순으로 물러나며 어느 단계에서도 화면이 비지 않는다.

12
Troubleshooting

원인을 찾는 데 가장 오래 걸린 4가지

넷 다 실패했다는 신호가 없었다. 예외도, 에러 응답도, 화면 변화도 없이 어긋났다.

트랜잭션 · 알림
알림이 예외 없이 사라졌다
증상
약속에 초대하면 응답은 201, 로그도 깨끗한데 상대 알림함이 비어 있었다. 알림 기능 전체가 한 건도 저장되지 않았다.
원인
커밋 이후에 도는 리스너(AFTER_COMMIT)에서 저장했는데, 기본 전파 옵션이라 이미 커밋된 트랜잭션에 참여했다. 새로 커밋할 주체가 없어 INSERT가 조용히 버려졌다.
해결
알림 저장만 새 트랜잭션(REQUIRES_NEW)으로 떼어냈다. 커밋 이후 리스너에서 저장하려면 반드시 새 트랜잭션이어야 한다는 걸 주석으로 남겨, 새 도메인이 같은 자리를 다시 밟지 않게 했다.
비동기 · 알림 스트림
연결을 끊을 때마다 500이 쌓였다
증상
사용자에겐 아무 문제가 없는데 서버 로그에 Access Denied 스택트레이스가 계속 쌓였다. 재현 조건을 못 찾다가 탭을 닫을 때마다 난다는 걸 발견했다.
원인
실시간 알림(SSE)은 비동기 요청이라 끝날 때 필터체인을 한 번 더 탄다. 그 시점엔 인증 정보가 비어 있어 인가에 걸리는데, 응답은 이미 나간 뒤라 에러 페이지도 못 보내고 로그만 남았다.
해결
최초 진입에서 이미 인증했으므로 비동기 재진입은 통과시켰다. 연결을 강제로 끊고 70초 관찰해 0건을 확인했다.
멱등 · 리마인더 메일
중복 방지가 알림만 지키고 메일은 놓쳤다
증상
아직 터지지 않았지만, 터지면 5분마다 같은 메일이 나갈 자리였다.
원인
리마인더 배치는 5분마다 같은 일정을 다시 집는다. 중복 알림은 DB 유니크 제약이 걸러줬지만, 메일은 그 제약 바깥이라 걸러진 회차에도 그대로 발송됐다. 발송 자체는 성공하니 로그로도 안 보인다.
해결
알림이 실제로 새로 만들어졌을 때만 메일을 보내도록 저장 결과를 반환값으로 받아 게이트를 걸었다. 게이트를 일부러 지워 테스트가 실패하는 것까지 확인했다.
서비스 경계 · 개인화
양쪽 다 정상인데 개인화가 반영되지 않았다
증상
취향 데이터를 쌓아도 추천 카테고리가 그대로였다. be 로그 정상, 응답 200, 화면도 멀쩡했다.
원인
be 앞에 프록시를 세워 실제로 나가는 요청을 찍어보니 취향이 정확히 실려 있었다. 프로필을 정반대로 바꿔 던져도 결과가 한 글자도 안 변해서, 받는 쪽이 그 값을 안 쓴다는 걸 확인했다.
해결
경계 너머로 요청 원문을 캡처해 “보냈다”와 “썼다”를 분리해서 증명했다. 이후 추천 서버가 반영하도록 고쳤고, 프로필을 바꾸면 후보가 실제로 달라지는 것까지 검증했다.
13
Retrospective

회고 — 만드는 것보다 이어붙이는 게 어려웠다

기능은 대부분 만들었다. 시간을 가장 많이 쓴 건 새 기능이 아니라 이미 만든 것들이 서로 안 맞는 걸 찾아내는 일이었다.

“다 만들었다”는 말을 믿지 않게 됐다

  • 알림은 타입 11종에 저장 · 조회 · 실시간 푸시 · 메일까지 코드가 다 있었다. 그런데 실제로 발행되는 건 2종, 나머지 9종은 부를 사람이 없었다
  • 배관은 완성인데 물을 트는 곳이 없는 상태였고, 코드만 읽으면 완성으로 보인다. 전체를 한 번 돌려보기 전까지 아무도 몰랐다
  • 그 뒤로 뭔가 만들면 “코드가 있다”가 아니라 “실제로 불리는가”를 먼저 확인하게 됐다

조용한 실패가 제일 비쌌다

  • 가장 오래 걸린 네 건이 전부 아무 신호가 없는 실패였다
  • 알림은 예외 없이 사라졌고, 스트림은 사용자에겐 멀쩡한데 로그에만 500이 쌓였다
  • 메일은 발송에 성공하면서 같은 걸 반복해 보낼 참이었고, 개인화는 200 OK에 화면도 정상인데 값이 안 먹었다
  • 에러가 나면 차라리 쉽다. 에러가 안 나는데 틀린 것을 찾는 게 몇 배 오래 걸렸다

믿었던 자리에서 났다

  • @Transactional을 붙였으니 저장될 줄 알았다 — 커밋 이후에 도는 리스너에선 아니었다
  • 시큐리티를 설정했으니 요청이 한 번만 통과할 줄 알았다 — 비동기 요청은 두 번 탔다
  • DB에 유니크 제약을 걸었으니 중복이 막힐 줄 알았다 — 제약 바깥의 메일은 안 막혔다
  • 프레임워크가 알아서 해주는 범위를 정확히 모른 채 쓰고 있었다. 동작하니까 이해했다고 착각한 것들이었다

도메인을 나눈 값을 나중에 치렀다

  • 도메인별로 쪼개서 각자 빠르게 갔다. 그건 잘한 선택이었다고 생각한다. 문제는 사이를 보는 사람이 아무도 없었다는 것이다
  • 프론트가 쓰기 시작한 응답 필드가 서버에 없었고, 서버가 정성껏 보낸 개인화 값을 추천 서버가 쓰지 않고 있었다
  • 양쪽 다 자기 로그로는 정상이라, 통합해서 눈으로 볼 때까지 드러나지 않았다
  • 계약을 문서로 맞춘 게 원인이었다. 문서는 지키지 않아도 아무 일이 안 일어난다

검증을 눈으로 하면 놓친다

  • 시연 데이터를 넣고 건수를 확인했다. 친구 5, 할 일 13. 맞는 숫자였다
  • 그런데 실제로 조인해 보니 전부 존재하지 않는 사용자에게 붙어 있었다. 변수 하나가 빈 값이었는데 건수만 봐서는 정상으로 보였다
  • 지운 줄 알았던 데이터가 안 지워진 적도 있었다. 명령은 성공했고 에러도 없었다
  • “했다”와 “됐다”를 구분해서 확인하는 습관이 이 프로젝트에서 가장 크게 남은 것 같다

문서는 쓰는 순간부터 낡는다

  • 요구사항 문서에 ‘예정’으로 적힌 33건 중 31건은 이미 만들어져 있었다
  • README는 절반이 사실이 아니었다 — “이 도메인들은 아직 골격”이라고 적혀 있는데 다 구현돼 있었다
  • 문서를 안 쓴 게 아니라, 코드가 문서보다 빨리 움직였다. 다음엔 문서 대신 돌려보면 답이 나오는 스크립트를 남기고 싶다
다시 한다면 — 두 가지를 앞으로 당기겠다
통합해서 한 번 돌려보는 것을 훨씬 일찍. 마지막에 몰아서 하니 그때부터 문제가 쏟아졌다. 위의 불일치들은 며칠 먼저 잡을 수 있었다.
보안 설정을 나중으로 미루지 않기. 로컬에서 되는 값이 그대로 남았고, 지금도 쿠키 여섯 곳이 개발값이다. 처음부터 운영 기준으로 두고 로컬만 낮췄으면 잊을 일이 없었다.
